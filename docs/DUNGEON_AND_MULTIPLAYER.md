# 던전 · 멀티플레이 설계 노트

던전 씬 구조와 (향후) 멀티플레이 이식에 대한 설계 결정과 **그 근거**를 모은 문서입니다.
"버그처럼 보여도" 고치기 전에, 또는 같은 논의를 처음부터 다시 하기 전에 이 문서를 먼저 확인하세요.

상태 표기: ✅ 확정 · 🕒 나중 마일스톤(지금 구현 안 함) · 🚫 범위 밖

---

## 0. 범위와 전제

- 이 프로젝트는 **포트폴리오/공모전용**입니다. **상용 출시는 고려하지 않습니다.**
- 프로덕션 인프라(전용 서버 상시 가동 오케스트레이션, 매치메이킹, 스케일링, DDoS 대응, 비용)는 **범위 밖**입니다.
- **동시 다중 파티는 하지 않습니다.** 한 번에 **한 파티 / 한 세션**만. → 던전 인스턴싱·인터레스트 관리·2층 서버가 전부 불필요.
- 멀티는 **나중 마일스톤**입니다. 지금은 싱글로 완성하고, "멀티 대비 원칙"(§7)만 지켜 나중 전환 비용을 줄입니다.

## 1. 던전 씬 구조 — ✅ 확정

| 항목 | 결정 |
|---|---|
| 던전 씬 파일 | **Build Settings 씬** (어드레서블 씬 ❌) |
| 씬 식별 | **클래스 이름 = 씬 이름** 규약 유지(무조건). 던전마다 **자기 클래스 + 자기 씬**(예: `Dungeon1Scene`) |
| 던전 JSON 테이블 | **만들지 않음** (아래 근거) |
| 라이팅 · NavMesh | 각 던전 씬에 **네이티브 베이크** |
| 던전 콘텐츠(몬스터 · 이펙트 · BGM 프리팹) | **어드레서블** — 로드 + 풀링 + 이탈 시 Release |

### 왜 어드레서블 씬이 아니라 Build Settings인가

어드레서블 **씬**은 취약하며, 특히 "던전에 라이팅 베이크" 요구와 정면충돌.
1. **베이크 라이팅 깨짐** — 어드레서블 로드 씬은 라이트맵이 제대로 안 붙는 이슈(특히 additive, 라이트맵 인덱스 충돌).
2. **운영 취약성** — 콘텐츠 카탈로그 재빌드를 깜빡하면 런타임에 깨짐. 에디터는 Asset Database 모드로 번들 우회 → **에디터선 되고 빌드에선 깨지는** 함정.
3. **API 혼용 불가** — `SceneManager.LoadScene`으로 못 부름.
4. **미러 비호환** — 미러 씬 동기화(`ServerChangeScene`, online/offline)는 **Build Settings 씬 전제**. 어드레서블 씬은 커스텀 `NetworkSceneManager` 필요.

Build Settings면: 라이팅·NavMesh 네이티브 작동 / 현재 `GameSceneManager` 코드 그대로 / Single 모드라 이전 씬 자동 언로드(메모리 관리됨) / 던전 몇 개는 용량 무의미 / 미러 친화.

### 왜 던전 JSON 테이블을 안 만드는가

- "클래스 = 씬" 규약을 유지하면 던전마다 씬을 직접 지정하므로 **index→씬주소 매핑 테이블이 불필요**.
- 몬스터는 **핸드 오소링된 던전 씬에 직접 배치**(또는 씬이 스폰). 몬스터 **스탯**은 이미 있는 몬스터 테이블에서 옴 → **던전 전용 테이블 불필요**.
- 결과: `GameSceneManager`는 **손대지 않음**(Build Settings + 클래스별 씬이라 `SceneManager.LoadSceneAsync` 그대로).

### 정적 환경 vs 동적 콘텐츠 분리 (원칙)

- CLAUDE.md "씬 단위로 바뀌는 건 어드레서블" 방침의 진짜 의도는 **메모리 관리**이고 대상은 **콘텐츠**(몬스터·이펙트·BGM)이지 씬 파일이 아님.
- **라이팅 굽는 정적 환경(씬)** → Build Settings / **동적 콘텐츠** → 어드레서블. 동적 오브젝트는 베이크 라이트맵이 없어 어드레서블 취약성에 안 걸림.

### 어드레서블 씬이 정당한 경우 (참고)

수백 개 씬 · DLC · **패치로 내려받는 콘텐츠**. 이 프로젝트엔 해당 없음.

## 2. 씬 흐름 — ✅ 확정 (필수 구조)

```
로그인 → 부트스트랩(JSON 로드) → 마을(허브) → 던전(파티) → 마을
```

- 마을 = 코어 / Build Settings, 던전 = Build Settings 씬 + 어드레서블 콘텐츠.
- **마을 ↔ 던전 왕복은 무조건 이 구조** (던전은 마을을 통해서만 진입).
- 미러 **offline(마을) / online(던전)** 모델과 그대로 매핑(§3).
- JSON은 부트스트랩에서 1회 로드(`JsonManager.ReadyTask`, [BootstrapTest.cs](../Assets/Scripts/Scene/BootstrapTest.cs)가 await) → 이후 어디서든 동기 조회. 별도 로딩 순서 불필요.

## 3. 멀티플레이 설계(Mirror) — 🕒 나중 마일스톤 / 방향 ✅ 확정

| 항목 | 결정 |
|---|---|
| 프레임워크 | **Mirror** |
| 서버 모델 | **전용(headless) 서버 하나** (`StartServer`, `-batchmode -nographics`) |
| 동시 파티 | **없음** — 한 세션 = 한 파티 |
| 재접속 | **없음** (튕기면 아웃) |
| 드롭 견딤 | **아무도 호스트가 아니라, 누가 튕겨도 서버 생존 → 나머지 멀쩡** |
| 마을 / 던전 | 마을 = 로컬 월드 + 채팅/파티만 동기화 / 던전 = 움직이는 오브젝트 풀 동기화 |
| 세션 수명 | **마을 접속부터** (채팅·파티 때문에) ~ 던전 |

### 왜 전용 서버인가 (호스트=파티가 아니라)

- 요구사항: **호스트가 튕겨도 나머지가 멀쩡해야 함**(드롭 견딤).
- 호스트=파티는 호스트=서버라 **호스트 드롭 시 세션 사망**. 이를 막는 길은 둘뿐:
  - **호스트 마이그레이션** — 미러 내장 없음 + 최난도 + 코드 최소화 방침과 정반대. 🚫
  - **전용 서버** — 아무도 호스트가 아니게. **정답.**
- 미러는 `StartHost` ↔ `StartServer`만 달라 **코드 변경 거의 없음**. 전원이 클라이언트 → 누가 튕겨도 서버 생존.
- **포트폴리오 범위와 안 부딪힘**: 필요한 건 **headless 인스턴스 하나**(현장 데모 PC 한 대 또는 싼 VM). 오케스트레이션·매치메이킹·비용은 🚫 범위 밖.
- 같은 코드베이스가 호스트/전용서버 둘 다 → 지금 락인 없음.

### 왜 동시 다중 파티를 안 하는가 (중요)

- 동시 다중 파티면 "일부는 마을, 일부는 던전"이 한 서버에 공존 → 미러 `ServerChangeScene`은 **서버 전체 씬을 바꿔** 섞임 → **additive 씬 + 인터레스트 관리**(어려운 MMO-lite) 필요.
- **한 파티만** 하기로 해서 이 복잡도 전체를 회피. 전원이 함께 마을→던전 이동하므로 `ServerChangeScene` 그대로 됨.

### 마을 = 로컬 월드 + 채팅/파티만

- 마을은 **각자 로컬 월드**(다른 플레이어 이동·충돌 동기화 없음, 서로 안 보임).
- 네트워크로 흐르는 것은 **채팅 + 파티**뿐.

### 채팅 = 2채널 (기능)

- **일반 채팅** = 전체 broadcast (`ClientRpc` → 접속 전원).
- **파티 채팅** = 파티원만 (`TargetRpc` → 파티 커넥션).
- 채팅 매니저 `NetworkBehaviour` 하나에 채널 태그 + 수신자 필터링. (서버를 2개로 나누는 게 아님)

### 파티 시스템 = 레디체크 흐름

```
파티 신청 → 상대 받음 → 파티창(로스터) → "입장?" 수락 창 → 전원 수락 → 던전 씬 이동
```

| 흐름 | Mirror 구현 |
|---|---|
| 파티 로스터 | `PartyManager : NetworkBehaviour`의 **SyncList**(멤버 + 준비상태) |
| 신청 / 수락 | **Command**(클라→서버) + **TargetRpc**(서버→특정 클라) |
| "입장" 수락 | 준비 상태 SyncVar |
| 전원 수락 판정 | 서버가 확인 → **`ServerChangeScene(던전)`** |

### 미러 씬 관리 매핑

- offlineScene = 마을 / onlineScene = 던전.
- 던전 씬 전환은 **미러 `ServerChangeScene`이 몲**(전원 동기화 로드). 로컬 흐름(로그인)은 `GameSceneManager`.
- **경계 = 마을 → 던전 handoff** = 로컬 씬 관리 → 미러 씬 관리로 넘기는 지점.
- "던전은 멀티"는 Build Settings 결론을 **강화**함(미러 동기화 씬 = Build Settings 전제).

### 데모용 접속

- **LAN**(`NetworkDiscovery`) 또는 **직접 IP**면 현장 시연/영상 충분. 원격 필요 시 **Unity Relay 무료 티어**.

## 4. 상태 동기화 — ✅ 방향 확정 (최소 침습이 핵심)

### 방침: 이벤트 허브를 NetworkBehaviour로 감싸 코드 수정 최소화

- 아직 구현이 다 안 됐고 static 전역 상태가 **더 늘어날 가능성**이 있음. 전면 SyncVar 전환은 물려 있는 게 많아 머리 아프고 버그 위험 큼.
- 그래서: **static 이벤트 허브 → 오브젝트별 인스턴스로 전환**하되, **한 겹 `NetworkBehaviour`(릴레이)로 감싸** 기존 구독 코드 대부분을 유지. **판별은 미러 netId.**
- **서버 권위는 던전에만** 적용(마을 월드는 로컬이라 불필요, 마을은 채팅·파티만 네트워크).

### 왜 static 허브가 그대로면 안 되나

- 전용 서버(또는 호스트)는 한 프로그램에 **여러 플레이어 오브젝트**가 공존 → static 전역이면 **서로 상태를 공유해 꼬임**. 분리 단위는 **플레이어 오브젝트(netId)별**.
- **static은 네트워크를 못 건넘** — 평범한 함수 호출은 그 프로그램 메모리 안에서만 실행. 전송하려면 **NetworkBehaviour 위의 ClientRpc/TargetRpc/SyncVar**(netId로 배달)만 가능. → 감싸는 게 필연.

### 통로 분리 (성격 기준)

| 성격 | 통로 | 예 |
|---|---|---|
| 지속 상태(플레이어 소유) | SyncVar + hook (또는 릴레이) | HP · 레벨 · 인벤 · 퀘스트 진행 |
| 순간(휘발) 이벤트 | ClientRpc(릴레이) | 채팅 · 던전 클리어 · 보스 사망 |

- **재접속 없음 + 파티 동시 입장**이라 릴레이 방식의 유일 약점(늦은접속 상태)이 **애초에 안 생김** → 릴레이로 최소 침습 진행이 안전.
- 캐치: 릴레이 구독은 **오브젝트 디스폰 시 해제**(안 하면 누수·죽은 netId).

## 5. 플레이어 연속성(마을 ↔ 던전) — ✅ 확정

- 마을 = 로컬 플레이어 / 던전 = 네트워크 스폰 플레이어. **같은 GameObject를 네트워크 너머로 못 들고 감.**
- **연속성 = GameObject가 아니라 세이브 데이터(`GameSession`)** → 각 경계에서 플레이어 오브젝트 **재빌드**.
  - 마을: 세이브에서 로컬 플레이어 빌드.
  - 던전 입장: 로컬 정리 → 세이브 기반 네트워크 플레이어 스폰.
  - 던전 이탈: 네트워크 플레이어 정리 → 갱신된 세이브로 로컬 재빌드.
- 씬 전환 자동저장([GameSceneManager.cs](../Assets/Scripts/Managers/GameSceneManager.cs) `PlayerSaveService.SaveNow()`)이 이미 데이터 연속성 배관.
- `PlayerManager` 부트스트랩 모델은 멀티에서 **네트워크 스폰으로 재작업 필요**(예정).

## 6. 지금부터 지킬 원칙 (멀티 대비 · 코드 지침)

- **던전을 서버 권위로 설계** — 판정과 적용 분리(나중에 판정 = 서버 이관 쉽게). 히트 판정을 "입력→판정→데미지" 한 덩어리로 뭉치지 않기.
- 던전 입장의 **"씬 로드 스텝"을 갈아끼울 수 있게 분리**(로컬 `SceneManager` → 미러 `ServerChangeScene`).
- 던전 로더에서 **"누가 던전을 정하고 누가 적을 스폰하나"의 권위 경계를 함수로 분리**.
- **static 전역 상태를 새로 늘리지 않기** — 부득이하면 나중에 `NetworkBehaviour` 릴레이로 감쌀 수 있는 형태로.

## 8. 용어 메모

- **드롭 견딤**(= 연결 끊김 견딤) = 한 명이 튕겨도(연결 끊김) **서버와 나머지 플레이어는 멀쩡하게 게임을 이어가는 성질**. 공식 용어가 아니라 이 문서의 약칭. 호스트=파티는 호스트 튕김 시 서버가 죽어 전원 아웃이라 이 성질이 없고, **전용 서버**(서버 = 플레이어 아님)라야 확보됨. → §3 "전용 서버" 채택의 이유.
- **Single 모드** = 유니티 `LoadSceneMode.Single`(이전 씬 교체 로드). **싱글플레이/멀티플레이와 무관.**
- **세션** = 돌아가는 서버 하나. (이 프로젝트: 전용 headless 서버 하나 = 그 파티 세션)
- **전용 서버** = 플레이어가 아닌 중립 프로세스가 게임을 돎 → 호스트 드롭 없음.
- **릴레이(파사드)** = static 이벤트 허브를 `NetworkBehaviour`로 감싸 네트워크로 흘리는 최소 침습 방식.
