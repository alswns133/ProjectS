# 던전 입장 · 파티 구성 UI 기획 명세

던전 입장 창에서 파티를 꾸려 함께 들어가기까지의 UI 명세입니다.
**UI 구현 기준 문서**이며, 미러(네트워크) 구현은 범위가 아닙니다 — 필요한 접점은 §9 데이터 계약뿐입니다.

관련 문서: [DUNGEON_AND_MULTIPLAYER.md](DUNGEON_AND_MULTIPLAYER.md) §3 (전용 서버 · 동시 다중 파티 없음 · 레디체크 흐름)

**작성**: TH · **확정**: 2026-08-29 · **상태**: UI 기획 ✅ 확정 / 네트워크 연동 🕒 나중

> **2026-08-29 설계 변경.** 원래는 마을에 파티창을 두고 "근처 플레이어를 보고 초대"하는 구조였습니다.
> `DUNGEON_AND_MULTIPLAYER.md` §3에 **마을은 각자 로컬 월드(서로 안 보임)** 로 확정돼 있어,
> 마을에서 초대할 근거가 사라졌습니다. 그래서 초대 타이밍을 **던전 입장 시점으로 옮기고**
> 던전 입장 창과 합쳤습니다. 카드·목록·검색·정렬 규칙은 초대 목록 팝업으로 그대로 살아 있습니다.

## 0. 전제

| 항목 | 값 |
|---|---|
| 파티 정원 | **최대 2명** |
| 파티장 | **던전과 난이도를 고르고 초대를 보낸 사람** |
| 목록 범위 | **접속 중인 유저 전원** (마을이 로컬 월드라 "근처"라는 개념이 없음) |
| 선택 방식 | **단일 선택** |
| 네트워크 | Mirror 96.0.1 임포트만 된 상태 — **UI는 더미 데이터로 선행** |

파티 정원 2인이 설계를 크게 단순하게 만듭니다. 다중 선택도, 정원 계산도 필요 없고,
"상대가 파티중" = 곧 "만석"이라 초대 불가로 바로 떨어집니다.

## 1. 전체 흐름

```
[파티장]
  던전 입장 창 → 던전·난이도 선택
       ↓
  파티 슬롯의 빈 칸 클릭 → 초대 목록 팝업 → 한 명 선택 → 초대
       ↓  (이 순간부터 던전·난이도 변경 잠김)
                                    [파티원]
                          결성창이 열림 (초대자 · 던전 · 난이도 · 20초)
                                    ↓ 수락
       ←────────────── 파티 결성 ──────────────→
                     파티 결성창
       ↓
  파티장이 [던전 입장] → 결성창에 30초 카운트다운 시작
                                    ↓
                              파티원이 [던전 입장] → 즉시 두 명 다 입장
```

**핵심은 파티장이 방아쇠라는 점입니다.** 파티원에게는 별도의 "준비" 개념이 없고,
파티장이 출발을 걸면 30초 안에 확인만 하면 됩니다.

## 2. 던전 입장 창의 파티 슬롯

기존 던전 입장 창([DungeonEntryPopup.cs](../Assets/Scripts/UI/Popups/DungeonEntryPopup.cs))은
헤더·퀘스트 트래커·에피소드 목록·미리보기·난이도 탭·하단 버튼으로 이미 꽉 차 있습니다.
파티 UI는 **하단에 슬롯 두 칸**만 추가합니다.

```
파티  [ 나 ]  [ + ]                        [취소]  [입장]
```

- **파티가 2인이라 슬롯 두 칸이면 끝납니다.** 자리를 거의 안 먹고,
  "지금 누구와 들어가는가"가 입장 버튼 바로 옆에 항상 보입니다.
- **빈 슬롯 클릭** → 초대 목록 팝업(§3).
- **채워진 슬롯 클릭** → 내보내기(파티장) / 파티 나가기(파티원).
- 던전·난이도를 **고르기 전에는 빈 슬롯이 비활성**입니다. 어디로 갈지 정해지지 않으면
  초대받은 사람에게 보여줄 내용이 없습니다.

### 던전·난이도 변경 규칙

- **초대 응답을 기다리는 동안에만 잠깁니다.** 그 사이에 바꾸면 상대가 결성창에서 보고 있는 내용과
  달라지기 때문입니다. 초대를 취소하거나 응답이 오면 풀립니다.
- **파티가 형성된 뒤에는 파티장이 자유롭게 바꿀 수 있습니다.** 30초 카운트다운이 이미 동의 장치라,
  파티원이 원하지 않으면 출발 전에 나가면 됩니다. 던전을 바꿀 때마다 파티를 해체하고 다시 맺는
  성가심을 없애기 위한 결정입니다.
- 파티원은 던전·난이도를 **조작할 수 없습니다**(비활성 + 파티장의 선택이 표시됨).

바꿀 때 따라오는 규칙 둘:

- **파티원에게 알립니다** — "파티장이 던전을 ○○로 변경했습니다". 결성창에는 **현재 던전·난이도가
  항상 표시**돼야 합니다. 카운트다운이 시작됐을 때 어디로 가는지 모르면 30초 안에 판단할 수 없습니다.
- **카운트다운 중에 바꾸면 카운터가 취소됩니다.** 파티원이 확인하고 누르려던 목적지와 다른 곳에
  가게 둘 수 없습니다. 다시 [던전 입장]을 눌러 새로 시작합니다.

## 3. 초대 목록 팝업

빈 슬롯을 눌렀을 때 뜨는 팝업입니다.

| # | 요소 | 내용 |
|---|---|---|
| ① | 닫기 버튼 | 다른 UI와 동일한 위치·형태 |
| ② | 접속 중 탭 | 지금 접속해 있는 유저. 팝업을 열면 **항상 이 탭이 기본** |
| ③ | 최근 탭 | 파티로 던전을 클리어한 **서로 다른 10명**. 초대만 하고 안 돈 상대는 제외. 비접속이 섞임 |
| ④ | 플레이어 목록 | 카드 목록. 위에 가이드 행(온라인 · 플레이어 · 파티 가능 여부). **목록이 비어도 가이드 행은 유지** — 없앴다 다시 나타나면 레이아웃이 튐 |
| ⑤ | 검색창 | 탭 오른쪽. 닉네임 부분 일치. 접속 중 탭은 접속자만, **최근 탭은 비접속도 검색 대상**. 오른쪽 끝에 **새로고침 버튼** |
| ⑥ | 초대 수신 토글 | 현재 상태를 글자로 표시(`파티 초대 허용` / `파티 초대 거부`). 캐릭터 생성 시 허용으로 시작 |
| ⑦ | 파티 초대 버튼 | 선택한 한 명에게 초대. 응답이 올 때까지 **대기 상태**로 잠김 |

**최근 탭이 이 위치에서 더 잘 맞습니다.** "저번에 같이 깬 사람 다시 부르기"는
던전에 들어가려는 바로 이 순간에 하고 싶은 일입니다.

### ⑥ 의 저장 위치 — 캐릭터 세이브 (PlayerPrefs ❌)

PlayerPrefs는 **기기별**이라 다른 PC에서 로그인하면 설정이 날아갑니다. 더 중요한 건
**초대를 실제로 막는 판정은 서버가** 한다는 점이라, 서버가 이 값을 알아야 합니다.
→ `CharacterSaveData`에 필드를 추가하고, **기존 세이브에 필드가 없으면 허용**으로 간주합니다.

## 4. 카드 구조

카드는 세 구역입니다.

| 구역 | 내용 |
|---|---|
| ① | 접속 표시 — 작은 구체. **초록(온라인) / 회색 빈 원(오프라인)** |
| ② | **레벨 · 직업 아이콘 · 닉네임**. 각각 자리 고정 |
| ③ | 초대 가능 상태 — 짧은 텍스트 |

- **초록↔빨강을 쓰지 않는 이유**: 적록색맹이 구분하지 못하는 대표적인 조합이고, 구체가 작아 더 어렵습니다.
  색과 함께 **채움 여부로 형태까지** 다르게 해 색에만 기대지 않습니다.
- **② 의 자리를 고정하는 이유**: 직업명 길이가 달라지면 이름 시작 위치가 카드마다 어긋나 목록을 훑기 어려워집니다.
  직업은 검사·거너 두 종뿐이라(`CharacterSaveData.characterType`) 아이콘이면 충분하고 폭도 고정됩니다.
- 카드는 반드시 **프리팹 인스턴스**로 배치합니다. 이름은 `PartyPlayerCard` / 내부 `OnlineDot`·`NameText`·`InviteStateText`
  식 PascalCase — CLAUDE.md 씬·UI 이름 규칙.

## 5. 카드 상태

| 상태 | 카드 색 | 나타나는 탭 | 선택 | 비고 |
|---|---|---|---|---|
| 초대 가능 | 파랑 | 접속 중 · 최근 | ✅ | 선택 시 노랑 + 테두리 |
| 파티중 | 회색 | 접속 중 · 최근 | ❌ | 정원 2인이라 파티 소속 = 항상 만석 |
| 비허용 | 회색 | 접속 중 · 최근 | ❌ | 클릭하면 **그 카드가 진동** |
| 비접속 | 회색 | **최근 전용** | ❌ | ① 구체가 빈 원 |

> **"전투 중" 상태는 제거했습니다.** 던전 이동이 `ServerChangeScene`이라 전원이 함께 이동하고
> 동시 다중 파티도 없으므로, "일부만 던전에 있는" 상태가 애초에 생기지 않습니다.

### 회색은 한 가지 뜻만 갖습니다

**"지금 초대할 수 없음".** 왜 불가한지는 ①(접속)과 ③(상태)에서 읽습니다.
색에 사유까지 실으면 사유가 늘어날 때 규칙이 깨집니다.

## 6. 목록 갱신 · 정렬 · 초기화 · 빈 상태

### 갱신 — 상태는 실시간, 순서는 고정

갱신이 잦으면 카드가 재정렬되며 **클릭하려던 카드가 움직이고**, 뜸하면 이미 나간 사람에게
초대를 보내 실패만 늘어납니다.

> 카드의 ①③(접속·초대 가능 여부)은 갱신할 때마다 즉시 반영하되 **정렬은 다시 계산하지 않습니다.**
> 새로 들어온 사람은 목록 맨 아래에 붙고, 나간 사람의 카드만 사라집니다.

**정렬을 다시 계산하는 시점 — 네 가지뿐**: 팝업을 열 때 · 탭을 바꿀 때 · 새로고침을 누를 때 · 정렬 화살표를 누를 때.

### 갱신 방식 — 주기가 아니라 이벤트

**폴링하지 않습니다.** 서버가 접속자 목록을 `SyncList`로 들고 있으면 접속·이탈·파티 상태 변화가
생길 때만 델타가 날아오므로, "몇 초마다 물어본다"는 개념이 필요 없습니다.
폴링은 Mirror에서 오히려 부자연스러운 방식입니다.

- 폴링을 백업으로 둔다면 **5초** 정도면 이 규모(동시 접속 소수)에 충분합니다.
  1초 이하는 의미 없는 트래픽이고, 30초를 넘기면 이미 나간 사람에게 초대해 실패하는 일이 눈에 띕니다.
- **초대 목록 팝업이 열려 있는 동안에만 갱신합니다.** 닫혀 있는데 목록을 받아올 이유가 없습니다.
- UI 입장에서는 주기를 알 필요가 없습니다 — 데이터 계약에 "목록이 바뀌면 알려준다"만 있으면
  뷰는 다시 그리면 됩니다. 실제 값은 네트워크 담당자가 정합니다.

### 정렬

- **1차 — 초대 가능이 위, 불가가 아래.** 이 그룹 순서는 고정입니다.
  여기까지 뒤집히면 회색 카드가 맨 위로 올라와 목록이 쓸모없어집니다.
- **2차 — 닉네임순.** 가이드 행의 "플레이어"를 클릭하면 이 키만 뒤집히고, 방향은 ▲▼로 표시합니다.

**닉네임 순서는 C# 기본 문자열 정렬(`string.CompareTo`)을 그대로 씁니다.**
결과는 대략 **특수문자 · 숫자 → 영문 → 한글** 순입니다.

> ⚠️ 원래 의도는 "한글 → 영문 → 숫자, 특수문자는 맨 아래"였으나 기본 정렬로는
> **한글이 맨 뒤, 특수문자가 맨 앞**으로 갑니다. 커스텀 비교자를 만들지 않기로 해서 이 결과를 받아들입니다.
> 한글 닉네임이 다수라 아래쪽에 몰리는 것이 거슬리면, 첫 글자로 그룹 순위를 매기는
> 비교자(약 10줄)로 언제든 되돌릴 수 있습니다.

### 팝업을 닫았다 열 때 초기화

| 대상 | 값 |
|---|---|
| 탭 | 접속 중 탭 |
| 검색어 | 비움 |
| 선택 | 해제 |
| 정렬 방향 | 기본값 |
| 스크롤 | 맨 위 (탭 전환 시에도) |

### 선택이 풀리는 조건

원칙 하나로 통일합니다 — **보이는 것 = 선택 가능한 것 = 초대 대상.**

- **목록에서 사라지면 선택 해제.** 검색으로 걸러졌든, 갱신 중 상대가 나갔든 동일합니다.
  카드가 없는데 ⑦만 활성이면 **보이지 않는 사람에게 초대가 나갑니다.**
- 카드는 남아 있고 **상태만 바뀐 경우**(허용 → 비허용 등)는 선택을 유지하되,
  초대를 눌렀을 때 실패 팝업으로 알립니다.

목록에서 **자기 자신은 제외**합니다.

### 빈 상태

**팝업이 아니라 ④ 목록 영역 한가운데의 흐린 텍스트**로 표시합니다.
빈 상태는 유저의 행동에 대한 응답이 아니라 지금의 상태이고, 팝업은 치우고 나면
텅 빈 목록만 남아 결국 아무것도 설명하지 못합니다.

| 상황 | 문구 |
|---|---|
| 접속 중 탭 · 나뿐 | 접속 중인 다른 플레이어가 없습니다 |
| 최근 탭 · 기록 없음 | 함께 던전을 클리어한 기록이 없습니다 |
| 검색 결과 없음 | '하루'와 일치하는 플레이어가 없습니다<br>(접속 중 탭 보조 문구: 접속 중인 플레이어만 검색됩니다) |

- 문구는 **원인 + 다음에 할 것**으로 씁니다. "데이터 없음" 같은 시스템 말투는 아무것도 알려주지 않습니다.
- **로딩과 빈 상태를 구분합니다.** 서버 응답을 기다리는 동안에도 목록은 비어 있어서,
  구분하지 않으면 열 때마다 "플레이어가 없습니다"가 한 번 번쩍였다가 목록이 채워집니다.
  첫 응답 전에는 문구를 띄우지 않습니다.
- **팝업은 유저 행동에 대한 응답**(초대 실패, 거절당함, 시간 초과)에만 씁니다.

## 7. 초대 받기 — 별도 팝업 없이 결성창으로

초대를 받으면 **결성창이 그대로 열립니다.** 수락 전용 팝업을 따로 만들지 않습니다 —
어차피 수락하면 보게 될 창이고, 팝업을 거쳐 다시 창을 여는 단계가 낭비입니다.

즉 결성창에 **초대 대기**라는 상태가 하나 더 붙습니다(§8의 "파티 없음"까지 하면 셋).

| 상태 | 내용 |
|---|---|
| **초대 대기** | 상대 슬롯에 초대자(닉네임·레벨·직업), 내 슬롯은 "수락 대기". 던전 이름·난이도 표시. **수락 / 거절** 버튼 + 응답 제한 시간 |
| **파티 결성** | 슬롯 두 칸이 로스터. 파티장이면 [던전 입장], 파티원이면 대기 후 확인 (§8) |

- **파티 수락이 아니라 "이 던전에 같이 들어가기" 수락**이므로 던전 이름과 난이도가 반드시 보여야 합니다.
- **응답 제한 시간은 20초.** 초대자가 무한정 기다릴 수는 없습니다.
  §8의 30초 출발 카운트다운과 **시각적으로 구분**해야 합니다 — 둘 다 결성창 안에서 도는
  카운트다운이라 같은 모양이면 무엇이 끝나가는 것인지 헷갈립니다.
- 거절하거나 20초가 지나면 창이 닫히고 **초대자에게 결과를 알립니다**.
- **초대가 오면 결성창은 UI 최상위로 뜹니다.** 인벤토리·상점·던전 입장 창을 보고 있어도 그 위로
  올라옵니다 — 초대를 놓치는 쪽이 하던 일이 끊기는 것보다 나쁩니다.

## 8. 파티 결성창과 30초 카운트다운

파티가 형성되면 던전 입장 창이 파티 결성 상태가 됩니다. 슬롯 두 칸이 로스터,
입장 버튼이 레디 역할을 합니다.

### 파티는 던전 클리어와 함께 해체된다

파티의 수명은 **결성 ~ 던전 클리어**까지입니다. 클리어하고 마을로 돌아오면 해체됩니다.
한때 "클리어 뒤에도 유지"를 검토했으나 §12의 이유로 철회했습니다.

### 결성창은 파티가 있는 동안만 존재한다

파티 초대 목록이 던전 입장 창 안으로 들어갔기 때문에, **파티가 없을 때 결성창에는 열 내용이 없습니다.**
반대로 파티가 있는 동안에는 **반드시 다시 열 수 있어야 합니다** — 파티를 맺고 던전 입장 창을 닫은 뒤
마을을 돌아다니다가 상태 확인·출발·나가기를 하려고 게이트까지 다시 걸어가는 건 말이 되지 않습니다.

> **파티가 생기면 HUD에 진입점이 나타나고, 파티가 해체되면 진입점도 사라진다.**

진입점은 둘입니다.

- **단축키 `Tab` — 마을에서만.** 인게임에서 비어 있는 키입니다(인증 화면의
  [FormNavigation](../Assets/Scripts/UI/Auth/FormNavigation.cs)이 Tab을 쓰지만 다른 씬이라 충돌하지 않음).
  **던전 안에서는 비활성**입니다 — 이미 들어와 있어 결성창에 할 일이 없고,
  전투 중 창이 열리는 것만 위험합니다. 던전 안의 파티 정보는 파티현황창(HUD)이 담당합니다.
- **파티현황창(HUD) 클릭.** 파티가 있을 때만 뜨는 UI라 진입점의 생명주기가 정확히 일치합니다.

### 파티가 없을 때도 열린다

마을에서 Tab을 누르면 **파티가 없어도 결성창이 열립니다.** 아무 반응이 없으면 키가 먹은 것인지
창이 없는 것인지 알 수 없기 때문입니다. 이때는 모든 기능이 비활성입니다.

빈 창에 버튼만 회색으로 늘어놓지는 않습니다 — **다음에 할 것을 한 줄로 안내**합니다
(§6 빈 상태 원칙과 같습니다). 예: "던전 입구에서 파티를 만들 수 있습니다".

그래서 결성창은 상태가 셋입니다: **파티 없음 · 초대 대기 · 파티 결성**.

> ⚠️ **채팅 입력 중에는 Tab이 결성창을 열면 안 됩니다.** 채팅은
> [DUNGEON_AND_MULTIPLAYER.md](DUNGEON_AND_MULTIPLAYER.md) §3에 예정돼 있고, 입력 중 게임플레이
> 단축키를 막는 규칙이 없으면 이름을 치다가 창이 열립니다. 또 Tab은 채팅 채널 전환에도 흔히 쓰이는
> 키라, 채팅을 붙일 때 배치가 겹치지 않는지 한 번 확인해야 합니다.

**파티현황창에 기능을 넣지는 않습니다.** 그쪽은 레벨·닉네임·HP·SG를 보여주는 전투 정보 HUD이고,
결성창은 마을에서 출발을 준비하는 창이라 쓰이는 시간이 거의 겹치지 않습니다
(던전 안에서는 결성창에 할 일이 없고, 마을에서는 파티원 HP를 볼 이유가 적습니다).
전투 중 계속 떠 있는 HUD에 "파티 나가기" 같은 버튼을 두면 오조작 위험도 큽니다.
→ **던전 안에서는 파티현황창 클릭을 막습니다.**

**던전 변경은 던전 입장 창을 재사용합니다.** 결성창에서 "던전 변경"을 누르면 기존
[DungeonEntryPopup](../Assets/Scripts/UI/Popups/DungeonEntryPopup.cs)이 열리고, 고르면 결성창으로
돌아옵니다. 결성창 안에 에피소드 목록·난이도 탭을 다시 만들지 않습니다 — 그 팝업은 이미
`SetMode`로 던전·레이드를 공유하도록 만들어져 있어 재사용에 맞습니다.

### 출발 규칙

| 상황 | 동작 |
|---|---|
| 파티장이 [던전 입장] | **30초 카운트다운 시작**. 파티장 화면은 "파티원 대기 중 00:23" |
| 파티원이 [던전 입장] | **카운터와 무관하게 즉시 두 명 다 입장** |
| 카운트 중 파티장이 [취소] | **카운터 비활성화 · 입장 취소.** 파티는 유지된다 |
| 카운트 중 파티원이 파티를 나감 | **카운터 비활성화 · 입장 취소** |
| 30초 안에 파티원이 누르지 않음 | **파티 해체.** 양쪽에 "파티가 해체되었습니다" 알림만 띄운다. **"혼자 출발할까요?"는 묻지 않는다** — 혼자 가려면 파티를 해체하는 선택지가 이미 있고, 해체된 뒤 던전 입장 창에서 그냥 입장하면 된다 |
| **파티장이 파티를 나감** | **파티장이 파티원에게 계승된다.** 파티는 해체되지 않고, 남은 사람이 던전·난이도 선택권과 출발 권한을 갖는다. **던전·난이도는 원래 파티장의 선택을 그대로 유지**한다 |

- **파티원의 입장 버튼은 카운트다운이 시작되기 전까지 비활성**입니다.
  비활성 상태에 이유를 적어 둡니다 — "파티장이 출발을 시작하면 활성화됩니다".
- 카운트다운은 숫자와 함께 **진행 바**로 보여주고, 마지막 5초는 강조합니다.
  30초는 "읽고 판단할 시간"이라 남은 양이 감각적으로 보여야 합니다.
- 30초 만료로 해체될 때 **파티원 쪽에도 "파티가 해체되었습니다" 알림**이 필요합니다.
  자기가 시간을 넘겨서 해체된 것이라도, 아무 안내 없이 슬롯이 비면 버그로 보입니다.
- **파티장 계승 시에도 알림**이 필요합니다 — 던전·난이도 선택이 갑자기 활성화되는데
  이유를 모르면 혼란스럽습니다. "파티장이 되었습니다" 한 줄이면 충분합니다.

### 난입(늦은 입장)은 없다 — 그래서 카운트다운이 있다

**이미 진행 중인 던전에 나중에 합류하는 것은 지원하지 않습니다.**
미러 자체는 늦은 접속을 지원하지만(접속 시점의 씬을 로드시키고 존재하는 `NetworkIdentity`와
SyncVar 현재 값을 전달), 이 프로젝트 구조에서는 성립하지 않습니다.

- [DUNGEON_AND_MULTIPLAYER.md](DUNGEON_AND_MULTIPLAYER.md) §4가 순간 이벤트를 **ClientRpc 릴레이**로
  흘리기로 했고, 이는 "지나간 이벤트는 다시 못 받는다"는 뜻입니다. 그 문서는 이 약점을
  **"재접속 없음 + 파티 동시 입장이라 늦은접속 상태가 애초에 안 생긴다"** 는 근거로 넘어갔습니다.
- 진짜 비용은 연결이 아니라 **상태 맞추기**입니다. SyncVar로 덮이지 않은 것(몬스터 HP·어그로,
  애니메이터, 진행 타이머, 이미 떨어진 드랍, 열린 문)은 난입자에게 전부 기본값으로 보입니다.
- §7에 **재접속/복구가 범위 밖(🚫)** 으로 명시돼 있습니다.

→ **30초 카운트다운은 이 제약의 결과입니다.** 같이 들어가지 않으면 못 들어가므로 출발에 시간 제한이 필요합니다.
난입을 도입하려면 UI가 아니라 네트워크 설계를 바꿔야 하며, 그 문서 §7을 다시 열어야 합니다.

## 9. 최근 목록 저장

최근 탭은 저장하지 않으면 재접속할 때마다 비어버립니다.
던전을 **클리어 성공**한 시점에만 캐릭터 세이브에 한 줄씩 남깁니다
(중도 이탈·실패는 "같이 깼던 사람"이라는 이 탭의 정의에 맞지 않아 제외).

| 필드 | 용도 |
|---|---|
| `id` | 진짜 키. 초대 시 서버에 넘기는 값이고 중복 판정 기준 |
| `nickname` | 오프라인이면 서버가 알려줄 수 없으므로 저장본을 표시 |
| `level` · `characterType` | 오프라인 카드의 ② 구역을 채움 |
| `clearedAt` | 최근 순 정렬 + 10명이 넘칠 때 밀어낼 대상 선정 |

- **`level`·`characterType`을 낡은 값이어도 저장하는 이유**: 비워두면 카드 ② 구역이 반쯤 비어
  목록이 들쭉날쭉해집니다. 레벨이 조금 틀려도 알아보는 데는 지장이 없습니다.
- **"10"은 클리어 횟수가 아니라 서로 다른 사람 수입니다.** 같은 상대와 또 돌면 새 줄이 생기지 않고
  `clearedAt`만 갱신되어 위로 올라옵니다. 클리어 10회로 세면 고정 파티원이 있는 유저는
  목록에 한 명만 남아 탭이 사실상 비어버립니다.

## 10. 네트워크 담당자와의 접점

목록 한 줄에 필요한 데이터입니다. 식별자 타입은 네트워크 담당자가 정하고
UI는 그대로 들고 있다가 돌려주기만 합니다.

| 필드 | 용도 |
|---|---|
| `id` | 클릭 시 서버에 되돌려줄 식별자. 타입은 담당자 결정 |
| `nickname` | 표시·검색·정렬 기준. 전 서버 유니크라 키 역할 겸함 |
| `level` | ② 구역 표시 |
| `characterType` | 직업 아이콘 선택 (검사 / 거너) |
| `isOnline` | ① 구체 |
| `inviteState` | 초대 가능 / 파티중 / 비허용 — ③ 구역과 선택 가능 여부 결정 |

초대 요청에는 **대상 식별자 + 던전 ID + 난이도**가 함께 실려야 합니다(수락 팝업에 표시할 내용).

### 초대 흐름

```
[클라 A] 카드 선택 후 ⑦ 클릭 → 대상 식별자 + 던전 + 난이도를 실어 요청
   └ [서버] 검증 — 존재 / 접속 중 / 허용 / 양쪽 다 무소속
        └ [클라 B] 수락 팝업 (초대자 + 던전 + 난이도 + 타임아웃)
             └ [서버] 파티 확정 후 양쪽에 결과 전달
```

- 클라이언트끼리 직접 주고받지 않습니다. **검증은 전부 서버**에서 하며, 클라이언트가 보내는 것은 요청일 뿐입니다.
- 클라이언트가 가진 정보는 **갱신 시점 기준이라 늘 뒤처질 수 있습니다.** UI에서 걸러도 서버가 초대 시점에 다시 검증해야 합니다.
- 입장 확정(둘 다 눌렀거나 파티원이 즉시 입장)은 서버가 판정하고 `ServerChangeScene`으로 전원을 옮깁니다.

### UI가 미리 확보해 둘 상태

초대는 왕복에 시간이 걸리고 실패할 수 있습니다 — 대기 중("초대 중…"), 거절당함, 응답 없이 시간 초과,
실패 사유 표시. 나중에 끼워 넣으면 레이아웃이 흔들립니다.

UI 기획은 닫혔습니다. 남은 것은 네트워크 연동 시점에 정할 값뿐입니다.

- **목록 갱신 방식의 실제 구현** — 이벤트 푸시가 기본이고, 폴링 백업을 둘지와 그 주기(§6).

## 12. 파티 지속을 검토했다가 철회한 기록

같은 논의를 처음부터 다시 하지 않기 위해 남깁니다.

한때 **파티를 던전 클리어 뒤에도 유지**하기로 했습니다. 던전을 바꿀 때마다 파티를 해체하고
다시 맺는 성가심을 없애려는 의도였습니다. 그러나
[DUNGEON_AND_MULTIPLAYER.md](DUNGEON_AND_MULTIPLAYER.md) §3의 **"한 세션 = 한 파티"** 와 부딪혀 철회했습니다.

### 왜 부딪히는가 — 던전은 인스턴스가 아니다

- 전용 서버 **프로세스 하나**가 돌고, 그 프로세스는 **한 번에 씬 하나**만 갖습니다.
- 던전 진입은 `ServerChangeScene(던전)` — **서버의 씬을 통째로 바꾸고 연결된 모든 클라이언트에게
  그 씬을 로드시킵니다.**
- 던전 인스턴싱(additive 씬 + 인터레스트 관리)은 §7에서 범위 밖(🚫)입니다.

즉 **서버 하나 = 씬 하나 = 던전 하나 = 파티 하나**입니다.
파티가 해체되지 않고 유지되면, 두 사람이 파티를 맺는 순간 **나머지 접속자 전원이 영구히 초대 불가**가
되고 초대 목록의 모든 카드가 회색이 됩니다.

> ⚠️ **"마을은 로컬 월드니 여러 파티가 공존해도 된다"는 성립하지 않습니다.**
> 마을 월드가 로컬이어도 클라이언트는 채팅·파티 때문에 서버에 연결돼 있고,
> `ServerChangeScene`은 **연결된 전원**에게 씬 로드를 시킵니다. 한 파티가 던전에 들어가면
> 마을에 남으려던 다른 파티까지 딸려 갑니다.

### 검토한 대안과 결론

| 안 | 대가 |
|---|---|
| 동시 1파티 제약을 그냥 수용 | 시연에서 두 파티가 동시에 돌 일이 없다면 드러나지 않지만, 제약 자체는 남음 |
| 마을 서버 / 던전 서버 분리 (진짜 인스턴스) | 프로세스 2개 관리 — §7 "오케스트레이션 범위 밖" |
| **파티 지속 포기** ✅ | 던전 변경 시 재결성 부담이 남지만, 아키텍처를 건드리지 않음 |

→ **파티 지속을 포기**하고 클리어와 함께 해체하는 것으로 확정했습니다(§8).
파티가 짧게 살고 사라지므로 "한 세션 = 한 파티" 제약이 실사용에서 드러나지 않습니다.
