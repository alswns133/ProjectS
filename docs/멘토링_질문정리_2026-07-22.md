# 클라이언트 멘토링 질문 정리 (2026-07-22 작성 · 2026-08-07 개정)

Unity 3D 액션 RPG 팀 프로젝트입니다. 플레이어 전투(콤보·스킬·구르기·피격·공중대시), 몬스터 AI(상태 머신),
UI 프레임워크(Panel/Popup/Presenter), 씬 전환, 사운드, Addressables 기반 데이터 로딩까지 구현돼 있고,
**7월 말~8월 초 사이에 인벤토리·퀘스트 코어와 Firebase 기반 세이브/로드까지 실제 구현이 들어갔습니다.**
그 과정에서 몇 가지 구조적 결정(전투 타이밍의 SMB/태그 이관, 자유이동 캐릭터 이관에 따른 이동 잠금 2모델,
슈퍼아머, 씬별 애니메이터 컨트롤러, ID 넘버링 표준, 클라우드 세이브 선택)이 새로 생겼습니다.

> **개정 메모(2026-08-07)**: 최초 작성 시점의 "구현 전 사전 질문"이었던 6번(인벤토리/퀘스트/세이브)은
> 이제 대부분 **구현 후 검증 질문**으로 성격이 바뀌었습니다. 또한 작성 이후 생긴 주제(전투 타이밍 SMB 이관,
> 다중 캐릭터/씬별 컨트롤러)를 반영해 2번·4번을 손보고 **9번(다중 플레이어블 캐릭터 아키텍처)** 을 새로 추가했습니다.

각 질문은 **[현재 구현] → [우리의 선택과 이유] → [질문]** 순서로 정리했습니다.

## 1. 클래스 구조 전반

**현재 구현**
- `Player`와 `Enemy`를 "중앙 컨텍스트"로 두고, 기능을 역할별 컴포넌트로 분리했습니다.
  - Player: `PlayerInputHandler` / `PlayerMovement` / `PlayerAnimation` / `PlayerCombat` / `PlayerStats`
  - Enemy: `EnemyMovement` / `EnemyAnimation` / `EnemyCombat` / `EnemyStats`
- 컴포넌트 참조는 `Awake`에서 1회 캐싱하고 `{ get; private set; }` 프로퍼티로 공개합니다.
- 행동 제어는 상태 머신(`IState` → `BaseState` → 구체 상태)으로 하고,
  전환은 반드시 `StateMachine.ChangeState()`를 거쳐 Exit/Enter 순서를 보장합니다.
- **(작성 이후 추가)** 몬스터 근접/원거리는 클래스를 파생하지 않고 `EnemyCombat`의 공격 패턴 `kind`(Melee/Projectile)로
  구분합니다. 궁수 같은 혼합 몬스터도 슬롯 조합만으로 만들도록 했습니다.
- **(작성 이후 추가)** 플레이어 생성/유지는 `PlayerManager`(부트스트랩에서 1회 생성 → 비활성 유지 →
  씬 진입 시 워프+활성)가 담당합니다. 로그인/캐릭터 선택 결과를 들고 다니는 `GameSession`(static)과 짝을 이룹니다.

**우리의 선택과 이유**
- 한 클래스가 비대해지는 것을 막고, 팀원별로 파일 단위 분업이 가능하도록 역할별로 쪼갰습니다.
- Player와 Enemy가 거의 같은 구조(Stats/Movement/Animation/Combat + 상태 머신)를 각각 따로 가지고 있는데,
  공통 베이스 클래스로 묶는 것도 고민했지만 "이동 방식이 다르다(CharacterController vs NavMeshAgent)"는
  이유로 일단 분리 유지 중입니다.

**질문**
1. 스킬·몬스터 종류가 수십 개 규모로 늘어날 때, 이 "컨텍스트 + 역할 컴포넌트 + 상태 머신" 패턴이
   어디서 먼저 한계가 오는지 궁금합니다.
2. Player/Enemy의 중복 구조를 공통 베이스로 묶을 가치가 있는지, 아니면 실무에서도
   "비슷해 보여도 캐릭터와 AI는 분리 유지"가 일반적인지 궁금합니다.
3. **(추가)** 몬스터 근접/원거리를 서브클래스가 아니라 `kind` 값 + 슬롯 조합으로 표현하는 방식이,
   패턴이 복잡해질 때(예: 페이즈 전환, 소환, 버프)까지 버티는지, 아니면 어느 시점에 다시
   상속/컴포지션으로 갈아타는 기준이 있는지 궁금합니다.

## 2. 전투 타이밍 — Animation Event에서 SMB·태그 하이브리드로 이동한 뒤

**현재 구현**
- 히트 판정 프레임, 콤보/강공격/대시 히트 게이트, 이펙트·투사체 스폰은 여전히 애니메이션 클립의
  **Animation Event**로 연결합니다. 이벤트의 string 인자를 키로 히트박스 슬롯(`HitBoxSlot`)/투사체 슬롯(`ProjectileSlot`)을
  조회합니다. (작성 이후) 클립 저작자마다 `Attack_1` vs `Attack1`처럼 언더바 표기가 갈려 히트가 조용히 씹히던 문제가 있어,
  슬롯 조회·게이트를 `AnimationEventKey.Normalize`(언더바 제거)로 통일했습니다.
- **(작성 이후 크게 바뀐 부분) 이동 잠금·콤보 캔슬 창·루프 제어는 코드 타이머에서 벗어나
  `StateMachineBehaviour`(SMB) + Animator State Tag 조합으로 옮겼습니다.** 현재 5종:
  - `ComboResetBehaviour`: 로코모션 State 진입 시 `UnlockMovement`/`ResetCombo`(공격 종료 복귀 처리).
  - `AttackCancelBehaviour`: 각 공격 State에서 진행도가 `cancelWindowStart`를 넘으면 다음 입력(연계·캔슬 창)을 연다.
  - `StateBoolFlagBehaviour`: State 활성 동안 지정 Bool을 켜서 "지금 이 State인가"를 다른 전이 조건으로 쓴다(예: 대형 피격 중 약 피격 차단).
  - `IdleVariationBehaviour`: 대기 특수 모션 랜덤 발동.
  - `JumpAttackLoopBehaviour`: 공중 공격 Loop 진입 시 하강 시작.
- 자유이동 캐릭터(Haru)는 아예 **Animator State Tag("Attack"/"Hit") + 클립 종료**를 판정의 원천으로 삼아,
  매 프레임 태그로 이동 잠금·콤보 캔슬 창·공중 대시 캔슬을 재계산합니다(4번·9번과 연결).
- 판정은 인스펙터에서 배치한 히트박스 기준 `Physics.OverlapBoxNonAlloc`을 사용합니다.

**우리의 선택과 이유**
- 최초엔 "타이머보다 모션 보면서 이벤트 위치를 잡는 게 기획·애니메이션 수정에 유연하다"고 판단해 전부 Animation Event로 뒀는데,
  캔슬(구르기·피격)로 공격이 끊기면 클립에 심은 이벤트가 호출되지 않거나 뒤늦게 도착해 **래치된 트리거가 남아
  "유령 구르기/유령 피격 모션"** 이 재생되는 문제가 반복됐습니다. 이를 막는 방어 코드가 여러 곳에 늘었습니다.
- 그래서 **"단발 판정(히트 프레임·스폰)은 Animation Event, State에 종속된 상태 제어(이동 잠금·캔슬 창·루프·복귀)는
  SMB/태그"** 로 역할을 나눴습니다. SMB는 State가 실제로 활성/종료될 때 콜백이 오므로 "캔슬돼서 이벤트가 안 온다"는
  누락 자체가 줄어드는 게 기대였습니다.
- 다만 대가로 **판정 로직이 클립(이벤트) · SMB · 코드(태그 재계산) 세 군데에 흩어졌고**, State를 추가/편집할 때
  태그 부착·SMB 값·필요 파라미터를 함께 챙겨야 하는 규칙이 늘었습니다(빠뜨리면 안전 타임아웃까지 굳음).

**질문**
1. 지금의 **역할 분담(단발 판정=Animation Event / 상태 제어=SMB+태그)** 이 실무에서 통용되는 나눔인지,
   아니면 한쪽(전부 SMB, 혹은 전부 별도 타임라인/데이터)이 주도하도록 몰아주는 게 유지보수에 낫다고 보는지 궁금합니다.
2. "캔슬 시 이벤트 누락 → 방어 코드 증가"를 SMB/태그로 옮겨서 **줄였다기보다 다른 곳(태그·SMB 부착 규칙)으로 옮긴** 느낌인데,
   이 트레이드오프가 구조적으로 개선되는 패턴(예: 공격을 데이터로 기술하는 타임라인/스크립터블, 애니메이션과 로직의 분리)이 있는지 궁금합니다.
3. 판정이 세 군데(클립·SMB·코드)로 흩어진 상태에서, "이 공격이 몇 프레임에 뭘 하는지"를 팀이 한눈에 보게 하려면
   실무에선 무엇을 단일 소스로 두는지 궁금합니다.

## 3. static 이벤트 허브 방식

**현재 구현**
- 시스템 간 알림은 `PlayerEvents`, `CombatEvents`, `InventoryEvents`, `QuestEvents` 같은
  static 클래스의 C# 이벤트로 처리합니다. (작성 이후 인벤토리·퀘스트 허브가 실제 구독자까지 붙었습니다.)
- 외부에서 직접 Invoke하지 못하게 `FireXxx()` 발행 메서드만 공개하고,
  도메인 리로드를 꺼도 죽은 구독자가 남지 않도록 `[RuntimeInitializeOnLoadMethod]`에서
  전 이벤트를 null로 리셋합니다.
- UI는 Presenter(`HudPresenter` 등)가 이벤트를 구독해 View 메서드 호출로 변환합니다.
- 세이브 데이터는 이벤트 허브가 아니라 `GameSession`(static, 전체 세이브 운반) + `PlayerSaveService`로 따로 운반합니다
  ("알림"과 "상태 보관"을 구분).

**우리의 선택과 이유**
- 씬 어디서든 참조 연결 없이 발행/구독할 수 있어 결합도가 낮고 팀원이 쓰기 쉽다고 판단했습니다.
- 다만 새 이벤트를 추가할 때마다 리셋 메서드에도 수동으로 추가해야 하고(누락 시 조용히 버그),
  구독자가 많아지면 "이 이벤트를 누가 듣고 있는지" 추적이 어려워질 것이 걱정입니다.
  실제로 인벤토리/퀘스트가 붙으면서 허브 수와 구독자가 늘어나 이 우려가 조금씩 현실이 되고 있습니다.

**질문**
1. 프로젝트가 커졌을 때 static 이벤트 허브의 실제 한계가 무엇인지, 실무에서는 어느 규모부터
   다른 방식(ScriptableObject 이벤트 채널, 메시지 버스, DI 컨테이너 등)으로 넘어가는지 궁금합니다.
2. 지금 방식을 유지한다면, 이벤트가 늘어날 때 관리(리셋 누락 방지, 구독 추적)를 위해
   미리 잡아둘 규칙이 있을지 궁금합니다.
3. **(추가)** "알림용 이벤트 허브"와 "상태 보관용(`GameSession`)"을 나눈 지금 경계가 적절한지,
   세이브 대상 상태가 늘 때 이 둘이 섞이지 않게 유지하는 실무 기준이 있는지 궁금합니다.

## 4. 상태 머신의 경계 — 공격은 왜 상태가 아닌가

**현재 구현**
- 플레이어 상태는 `Free` / `Roll` / `Hit` / `Dead` / `JumpDash`(공중 대시) **5가지**입니다. (작성 시점 4개에서 `JumpDash` 추가.)
- 공격·콤보·스킬은 여전히 별도 상태가 아니라, Free 상태에서 `PlayerCombat`이 처리합니다.
  공격 중 이동 제한은 `Player.LockMovement()/UnlockMovement()`(또는 태그 기반 캐릭터는 `UpdateTagLock()`)로 조율합니다.
- 반면 몬스터는 `Idle / Patrol / Detect / Chase / Attack / Hit / Dead`로 공격이 상태입니다.
- **(작성 이후 추가된 결정 — 4번의 긴장을 키운 사례) 스킬 시전 중 슈퍼아머**:
  플레이어는 피해는 받되, 피격 경직(`PlayerHitState`) 진입 여부를 **"지금 무슨 동작 중인가"** 로 가릅니다.
  일반/대시/점프/강공격 중엔 정상 경직, **캐릭터 스킬 시전 중엔 슈퍼아머**(약 피격은 데미지만, 경직 생략).
  이 판정을 상태가 아니라 `PlayerCombat.IsCastingSkillMove` **플래그** + `PlayerStats.LastHitWasStrong`(강피격은 슈퍼아머 관통)으로 처리합니다.

**우리의 선택과 이유**
- 플레이어 공격은 "이동과 겹칠 수 있는 행동"(이동 중 공격 입력 버퍼, 콤보 유지)이라
  이동 상태와 직교로 두는 게 자연스럽다고 봤습니다.
- 다만 그 결과 Free 상태가 사실상 "이동 + 전투 전부"를 담게 되었고, 전투 관련 플래그
  (`IsCastingSkillMove`, `LastHitWasStrong`, 이동 잠금, 입력 버퍼, 태그 잠금)가 상태 머신 밖에서 늘어나는 중입니다.
  위 슈퍼아머가 대표 사례로, "경직이냐 아니냐"라는 상태급 판단을 상태가 아니라 플래그 조합으로 내리고 있습니다.
  새 행동(예: 가드, 차지 공격)이 추가될 때 어느 쪽에 둘지 기준이 애매해지고 있습니다.

**질문**
1. 플레이어 공격을 `AttackState`(및 `SkillState`)로 뽑는 것과 지금처럼 컴포넌트+플래그로 두는 것,
   실무 기준으로 어느 쪽이 유지보수에 유리한지 궁금합니다.
2. "상태로 만들 것 vs 플래그/컴포넌트로 둘 것"을 가르는 실무적 판단 기준이 있다면 알고 싶습니다.
   (특히 슈퍼아머처럼 "상태급 분기지만 이동과 직교"인 경우를 어디에 두는지.)
3. **(추가)** 몬스터는 공격이 상태인데 플레이어는 아니어서 두 상태 머신의 입도(granularity)가 다릅니다.
   이 비대칭을 유지하는 게 맞는지, 아니면 맞추는 게 나은지 궁금합니다.

## 5. 데이터/에셋 운영 기준 검증

**현재 구현**
- JSON 테이블: `IDataRow` 행 + `JsonManager`가 Addressables `TextAsset`을 비동기 로드·검증·캐싱.
  (작성 이후 등급 옵션·소비 아이템 등 실제 테이블이 JSON으로 넘어오며 등록 흐름이 돌기 시작했습니다.)
- 자체 기준을 세웠습니다.
  - JSON으로 뽑는 것: 기획자가 바꿀 밸런스 수치, 종류가 늘어나는 데이터
    (우선순위: 몬스터 스탯 > 스킬 > 아이템/드랍 > 퀘스트 > 플레이어 스탯). 아이템/퀘스트는 처음부터 JSON.
  - 인스펙터에 남기는 것: 프리팹·Transform 참조, 히트박스 배치, 연출 감각 값, 시스템 튜닝 값.
  - Addressables 그룹은 자산 종류가 아니라 **수명 기준**으로 분류
    (항상 메모리에 있는 것은 제외, 씬 단위로 바뀌는 것만 등록, 공유 자원은 Shared 그룹).
  - 프리팹은 주소 문자열로 `LoadAssetAsync` 1회 로드 후 풀링(`PooledSpawner`)으로 인스턴스화.
    `InstantiateAsync`는 풀링과 참조 카운트가 충돌해서 쓰지 않기로 했습니다.
- **(작성 이후 추가) ID 넘버링 표준**을 `docs/ID_NUMBERING.md`로 확정했습니다(몬스터/아이템/스킬/퀘스트/던전 자릿수 규칙).
  ID가 값을 인코딩하고 컬럼에도 같은 값이 있으면 `Validate(out error)`에서 둘의 일치를 검사해 오타를 로딩 시점에 거릅니다.
- asmdef(어셈블리 정의)는 현 규모에서 도입하지 않기로 **재확인**했습니다
  (컴파일 시간 이득이 없고, Player↔Enemy 상호 참조 구조상 리팩토링 비용만 발생한다고 판단).

**질문**
1. "밸런스 수치는 JSON, 시스템 튜닝 값은 인스펙터"라는 분리 기준이 실무 관행과 맞는지,
   놓치고 있는 예외가 있는지 궁금합니다.
2. Addressables를 수명 기준으로 그룹핑하는 방침이 맞는지, 규모가 커질 때 주의할 점이 있는지 궁금합니다.
3. asmdef 미도입 결정이 적절한지, 도입한다면 어느 시점·어떤 단위가 실무적으로 적당한지 궁금합니다.
4. **(추가)** ID가 값을 인코딩하도록 설계하고 `Validate`에서 일치를 검사하는 방식이 실무에서 권장되는지,
   아니면 ID는 불투명하게 두고 의미는 컬럼에만 두는 게 나은지 궁금합니다(리네임·재분류 시 비용 관점).

## 6. 인벤토리·퀘스트·세이브 — 구현 후 검증 (작성 시점엔 "구현 전 사전 질문")

**현재 구현 (작성 이후 크게 진행됨)**
- **인벤토리(코어 완료, 2026-08-04)**: 보유·획득·소비 아이템 사용·세이브·I키 열기까지 구현.
  Popup 모델(다른 창과 공존)에 드래그 이동, 슬롯 위치는 PlayerPrefs에 저장. **장착·재료 통합은 아직 보류.**
- **퀘스트(데이터+매니저 코어 완료, 2026-07-28)**: `QuestManager` + `QuestData`/`QuestTable`.
  보상은 `QuestEvents` 구독자(`QuestRewardGranter`)가 지급합니다. **킬 소스 연결·트래커 UI·JSON 정식 등록은 다음 단계.**
- **세이브/로드(구현 완료, 2026-08-03) — SQLite가 아니라 Firebase로 갔습니다**:
  Firebase 인증 + Realtime DB 기반 **클라우드 세이브**. 슬롯 모델(생성→목록→선택→접속),
  `GameSession`(static, 전체 세이브 운반) + `PlayerSaveService`, pull 주입, 씬 전환 시 자동 저장(`AutoSaveTicker`),
  보안 규칙까지 포함. `CharacterSaveData`가 저장 스키마입니다. (프로젝트에 sqlite-net 패키지는 남아 있지만 세이브엔 미사용.)

**우리의 선택과 이유**
- 만들고 나서 구조를 고치는 비용이 크기 때문에 방향을 먼저 확인하고 싶었고, 그 사이 코어를 구현하며 몇 결정을 내렸습니다.
- 세이브를 로컬(SQLite/JSON 파일)이 아니라 **클라우드(Firebase)** 로 간 이유: 계정 기반 다기기·백업, 팀 규모에서 서버 직접 운영 부담 회피.
  Steam/AWS도 검토했으나 초기 구축 속도와 무료 구간을 보고 Firebase를 택했습니다.

**질문 (이제는 "이렇게 만들었는데 맞나"의 검증 성격)**
1. 인벤토리에서 아이템 **"정의(테이블)" vs "인스턴스(수량·강화 상태)"** 분리를 지금 구조로 잡았는데,
   장착·강화·재료 통합이 들어오기 전에 미리 손봐야 할 지점이 있는지 궁금합니다(특히 인스턴스에 고유 ID를 줄지 여부).
2. 퀘스트 진행 추적을 **이벤트 허브 구독 + `QuestManager`** 로 했는데, 조건이 복잡해질 때(AND/OR, 순차 단계, 카운트)
   별도 조건 시스템으로 분리해야 하는 규모의 기준이 있는지 궁금합니다.
3. **세이브를 클라우드(Firebase)로 간 선택**에 대해:
   - 로컬 캐시 없이 **클라우드 우선**인데, 오프라인/네트워크 실패 시 처리를 어느 수준까지 준비해야 하는지.
   - 세이브 **스키마 버전 관리/마이그레이션**(필드 추가·삭제 시 기존 세이브 호환)을 언제·어떻게 넣는 게 나중에 덜 고생인지.
   - 클라이언트가 직접 쓰는 구조라 **치팅/무결성**(클라이언트 신뢰) 우려가 있는데, 이 단계에서 보안 규칙만으로 충분한지, 서버 검증이 필요한 선은 어디인지.
4. **(추가)** 인벤토리 슬롯 위치를 PlayerPrefs에, 캐릭터 세이브는 Firebase에 두는 식으로 저장처가 갈렸는데,
   "무엇을 로컬 설정으로 두고 무엇을 계정 세이브에 넣을지" 가르는 실무 기준이 궁금합니다.

## 8. 폴더 구조와 에셋(리소스) 관리

**현재 구현**
- `Assets/Scripts`는 기능별 폴더(= 네임스페이스)로 정리 규칙이 잡혀 있지만,
  스크립트 외 에셋은 종류별 폴더(`Prefabs`, `Animator`, `Effect`, `Materials`, `Scenes`...)에
  넣는 방식이고 명확한 규칙 없이 커져 온 상태입니다. 구체적으로:
  - `Scenes/` 안에 실제 게임 씬(Bootstrap, InGame, Dungeon...)과 팀원별 작업 폴더(GC, JS, MJ, TH)가
    섞여 있습니다.
  - `Prefabs/` 루트에 낱개 프리팹과 하위 폴더(Dungeon, UI, Village)가 섞여 있습니다.
  - `Animator/`에 .fbx, .anim, .controller가 한 폴더에 섞여 있고, 네이밍도 제각각입니다
    (`Combo_Attack_03_01.anim`, `CLazy@Mvm_Walk.FBX`, 공백 포함 `NPC Idle.controller` 등).
  - 외부 에셋은 자체 규칙이 있습니다: **원본은 전부 `ExternalAssets/`에 두고
    (.gitignore로 깃 추적 제외 — 각자 로컬에만 존재), 커스텀하거나 수정해서 쓰는 것만
    밖으로 빼서 우리 폴더 체계로 분류해 깃으로 공유**합니다.
    다만 경계가 새는 지점이 생기고 있습니다 — `Assets/Synty`와 `ExternalAssets/Synty`가
    둘 다 존재하고(최상위 Synty는 ignore 대상이 아니라 깃에 올라감),
    `ExternalAssets/` 루트에 낱개 프리팹(SM_Prop_* 등)과 이미지가 굴러다니며,
    `Assets/DownloadCache/`의 .unitypackage 원본은 깃에 커밋되어 있습니다.
  - `Resources/` 폴더에 AudioMixer가 있습니다 (Addressables 통일 방침과의 관계 확인 필요).
- 리소스 로딩은 Addressables로 통일하는 방침이지만, 위처럼 폴더·이름 규칙은 아직 없습니다.

**우리의 선택과 이유**
- 스크립트는 "폴더 = 네임스페이스" 규칙으로 정리에 성공한 경험이 있어서,
  에셋 쪽도 규칙을 세우고 싶은데 기준을 무엇으로 잡을지(종류별 vs 기능/캐릭터별)가 고민입니다.
- 외부 에셋을 "원본은 `ExternalAssets/`(깃 제외)에 보존, 수정본만 밖으로 승격"으로 나눈 이유:
  원본을 건드리지 않으면 에셋 패키지를 재임포트·업데이트해도 커스텀이 날아가지 않고,
  대용량 원본 팩이 저장소를 불리지 않으며, 깃에 올라간 것만 보면
  "우리가 손대서 책임지는 에셋"이 무엇인지 구분되기 때문입니다.
- 팀원 4명이 각자 브랜치에서 작업하다 보니 팀원별 작업 폴더가 생겼는데,
  이게 임시 방편인지 실무에서도 쓰는 방식인지 모르겠습니다.

**질문**
1. 폴더 구조의 실무 기준이 궁금합니다 — 자산 종류별(`Prefabs/`, `Materials/`...)로 갈지,
   기능·캐릭터별(`Characters/Haru/` 아래에 프리팹+애니+머티리얼)로 갈지, 혼합이라면 경계를 어디에 두는지.
2. "원본은 깃 제외 벤더 폴더에 보존, 수정본만 밖으로 승격해 깃 공유"라는 우리 외부 에셋 규칙이
   실무 방식과 맞는지 궁금합니다. 특히:
   - 밖으로 뺀 수정본(깃에 올라감)이 여전히 `ExternalAssets/`(깃 제외) 안의 머티리얼·텍스처를
     참조하면, 해당 팩이 없는 팀원에게는 참조가 깨집니다. 의존성까지 같이 빼야 하는지(복제 비용)
     vs 참조를 유지하고 팩 설치를 전제하는지, 실무 기준이 궁금합니다.
   - 팀원 간 원본 팩 동기화는 현재 트렐로로 합니다: 외부 에셋을 쓸 사람이
     **원본 파일 + 메타파일을 압축해 트렐로에 올리고**, 팀원들이 받아서 `ExternalAssets/`에
     푸는 방식입니다(메타 포함이라 GUID가 유지되어 참조가 안 깨짐). 이 수동 공유 방식이
     실무에서도 통용되는지, 규모가 커지면 어떤 방식(팩 목록 매니페스트, 별도 스토리지,
     UPM 사설 레지스트리 등)으로 넘어가는지 궁금합니다.
   - 수정본이 어느 팩의 어떤 원본에서 왔는지 기록(출처 추적)은 어떻게 관리하는지 궁금합니다.
3. 팀원별 작업 씬/폴더(GC, JS, MJ, TH)는 실무에서도 쓰는 방식인지, 쓴다면 본 씬으로
   합치는 규칙을 어떻게 잡는지 궁금합니다.
4. 에셋 네이밍 컨벤션(접두사 규칙, 공백 금지 등)을 지금이라도 세우고 일괄 리네임할 가치가 있는지,
   리네임 시 씬/프리팹 참조가 깨지지 않게 주의할 점이 있는지 궁금합니다.
5. Addressables로 통일하는 방침에서 `Resources/` 폴더는 완전히 비우는 게 맞는지,
   AudioMixer처럼 남겨도 되는 예외가 있는지 궁금합니다.
6. `ExternalAssets/` 말고도 깃에서 빼야 할 것이 더 있는지 — Unity 프로젝트에서
   .gitignore 범위를 잡는 실무 체크리스트가 궁금합니다.

## 9. (신규) 다중 플레이어블 캐릭터 & 씬별 애니메이터 컨트롤러

**현재 구현 (작성 이후 생긴 주제)**
- 자유이동 3단 로코모션 캐릭터(Haru)를 이관하면서, 캐릭터마다 컨트롤러 규약이 달라
  **이동 잠금·콤보 연계 판정을 두 모델로 가르게 됐습니다.** 기준은 `PlayerAnimation.UsesMotionTags`
  (로코모션 bool `isMoving`/`isRunning` 존재 여부)이고 `Player.usesTags`로 캐싱합니다.
  - **태그 기반 모델**: Animator State Tag + 클립 종료가 판정 원천. `Player.UpdateTagLock()`이 매 프레임 재계산.
  - **기존 Z 블렌드 모델**: `ComboResetBehaviour` + `Player.maxActionLockTime` 안전 타이머로 관리.
- 같은 캐릭터도 **마을/던전에서 애니메이터 컨트롤러를 런타임 교체**합니다
  (`UseVillageController()`/`UseDungeonController()`, 던전은 `AnimatorOverrideController`).
  마을/던전은 파라미터 집합이 다른 별개 base라, 교체할 때마다 `RefreshParameterCache()`로 파라미터 존재 여부를 다시 계산합니다.
  씬 진입은 `Player.EnterVillage()`/`EnterDungeon()`가 호출하고, `combatEnabled`로 마을=전투 off, 던전=on을 가릅니다.

**우리의 선택과 이유**
- 캐릭터별로 애니메이션 저작 규약(태그 유무, 로코모션 bool 유무)이 갈리는 걸 코드 전체에 퍼뜨리지 않으려고,
  분기 지점을 `usesTags` 한 곳으로 모으고 나머지는 그 플래그로 두 경로를 태우는 방식을 택했습니다.
- 씬별로 아예 다른 컨트롤러를 두는 대신 하나를 런타임 교체한 건, 플레이어 인스턴스를 씬마다 새로 만들지 않고
  `PlayerManager`가 1회 생성한 인스턴스를 계속 쓰기 위해서입니다.

**질문**
1. "캐릭터마다 다른 애니메이터 규약"을 `usesTags` 같은 **단일 분기 플래그로 두 경로를 태우는 방식**이
   캐릭터가 3~4종으로 늘 때까지 버티는지, 아니면 캐릭터별 전략 객체(예: 캐릭터마다 `ILocomotionProfile`)로
   빼는 게 실무에선 표준인지 궁금합니다.
2. 씬(마을/던전)마다 **하나의 컨트롤러를 런타임 교체**하는 방식과, 아예 컨트롤러/상태머신을 분리해 두는 방식 중
   어느 쪽이 유지보수에 유리한지, 파라미터 집합이 다른 base를 오가는 지금 구조에서 주의할 점이 궁금합니다.
3. 캐릭터가 늘 때 애니메이터·상태 머신·전투 슬롯을 **캐릭터별로 얼마나 복제 vs 공유**하는 게 맞는지,
   공용 뼈대와 캐릭터 고유 부분을 가르는 실무 기준이 궁금합니다.

## 우선순위

시간이 제한적일 경우 **2번(전투 타이밍 SMB·태그 이관), 4번(공격의 상태 머신 경계), 9번(다중 캐릭터 아키텍처)**
순서로 여쭤보고 싶습니다. 이 셋은 앞으로 작성할 코드의 방향이 바뀌는 질문입니다.
그다음으로 **6번(인벤토리·퀘스트·세이브 검증)** — 특히 세이브를 클라우드로 간 선택과 스키마 버전 관리 — 을 확인하고 싶고,
나머지(1·3·5·7·8)는 이미 내린 결정의 검증이라 우선순위를 낮췄습니다.

> 최초 작성(2026-07-22)에서는 2·4·6 순이었으나, 6번의 세이브/인벤토리/퀘스트가 그 사이 구현되면서
> "방향 결정"의 무게가 9번(구현하며 새로 생긴 미결 구조)으로 옮겨갔습니다.
