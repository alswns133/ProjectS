# 클라이언트 멘토링 질문 정리 (2026-07-22)

Unity 3D 액션 RPG 팀 프로젝트입니다. 현재 플레이어 전투(콤보·스킬·구르기·피격), 몬스터 AI(상태 머신),
UI 프레임워크(Panel/Popup/Presenter), 씬 전환, 사운드, Addressables 기반 데이터 로딩까지 구현된 상태이고,
인벤토리·퀘스트·세이브는 데이터 구조만 잡아두고 본 구현 전입니다.

각 질문은 **[현재 구현] → [우리의 선택과 이유] → [질문]** 순서로 정리했습니다.

---

## 1. 클래스 구조 전반

**현재 구현**
- `Player`와 `Enemy`를 "중앙 컨텍스트"로 두고, 기능을 역할별 컴포넌트로 분리했습니다.
  - Player: `PlayerInputHandler` / `PlayerMovement` / `PlayerAnimation` / `PlayerCombat` / `PlayerStats`
  - Enemy: `EnemyMovement` / `EnemyAnimation` / `EnemyCombat` / `EnemyStats`
- 컴포넌트 참조는 `Awake`에서 1회 캐싱하고 `{ get; private set; }` 프로퍼티로 공개합니다.
- 행동 제어는 상태 머신(`IState` → `BaseState` → 구체 상태)으로 하고,
  전환은 반드시 `StateMachine.ChangeState()`를 거쳐 Exit/Enter 순서를 보장합니다.

**우리의 선택과 이유**
- 한 클래스가 비대해지는 것을 막고, 팀원별로 파일 단위 분업이 가능하도록 역할별로 쪼갰습니다.
- Player와 Enemy가 거의 같은 구조(Stats/Movement/Animation/Combat + 상태 머신)를 각각 따로 가지고 있는데,
  공통 베이스 클래스로 묶는 것도 고민했지만 "이동 방식이 다르다(CharacterController vs NavMeshAgent)"는
  이유로 일단 분리 유지 중입니다.

**질문**
1. 스킬·몬스터 종류가 수십 개 규모로 늘어날 때, 이 "컨텍스트 + 역할 컴포넌트 + 상태 머신" 패턴이
   어디서 먼저 한계가 오는지 궁금합니다.
2. Player/Enemy의 중복 구조를 공통 베이스로 묶을 가치가 있는지, 아니면 실무에서도
   "비슷해 보여도 캐릭터와 AI는 분리 유지"가 일반적인지 궁금합니다.

## 2. Animation Event 기반 전투 타이밍

**현재 구현**
- 히트 판정 프레임, 콤보 입력 가능 구간(콤보 윈도우), 콤보 리셋을 전부 애니메이션 클립의
  Animation Event로 연결했습니다.
- 이벤트의 string 인자를 키로 히트 박스 슬롯(`HitBoxSlot`)/투사체 슬롯(`ProjectileSlot`)을 조회해서,
  클립 이벤트만 봐도 어떤 판정·이펙트가 나가는지 읽히도록 이름 체계를 맞췄습니다.
- 판정은 인스펙터에서 배치한 히트 박스 기준 `Physics.OverlapBoxNonAlloc`을 사용합니다.

**우리의 선택과 이유**
- 타이밍을 코드 타이머로 잡는 것보다, 모션을 보면서 이벤트 위치를 조정하는 게
  기획·애니메이션 수정에 유연하다고 판단했습니다.
- 다만 비용도 체감하고 있습니다: 구르기·피격으로 공격이 캔슬되면 클립에 심어둔 이벤트가 호출되지 않거나
  뒤늦게 도착해서, 래치된 트리거가 남아 "유령 구르기/유령 피격 모션"이 재생되는 문제가 반복적으로 생겼고,
  이를 막는 정리 코드(`PlayerAnimation`의 트리거 리셋, `PlayerCombat`의 상태 확인 가드)가 여러 곳에 늘었습니다.

**질문**
1. 실무에서도 히트 프레임·콤보 윈도우를 Animation Event로 관리하는지, 아니면 다른 방식
   (예: StateMachineBehaviour, normalizedTime 기반, 별도 타임라인 데이터)을 쓰는지 궁금합니다.
2. "캔슬 시 이벤트 누락 → 방어 코드 증가"는 이 방식의 필연적 비용인지, 구조적으로 줄이는
   패턴이 있는지 궁금합니다.

## 3. static 이벤트 허브 방식

**현재 구현**
- 시스템 간 알림은 `PlayerEvents`, `CombatEvents`, `InventoryEvents`, `QuestEvents` 같은
  static 클래스의 C# 이벤트로 처리합니다.
- 외부에서 직접 Invoke하지 못하게 `FireXxx()` 발행 메서드만 공개하고,
  도메인 리로드를 꺼도 죽은 구독자가 남지 않도록 `[RuntimeInitializeOnLoadMethod]`에서
  전 이벤트를 null로 리셋합니다.
- UI는 Presenter(`HudPresenter` 등)가 이벤트를 구독해 View 메서드 호출로 변환합니다.

**우리의 선택과 이유**
- 씬 어디서든 참조 연결 없이 발행/구독할 수 있어 결합도가 낮고 팀원이 쓰기 쉽다고 판단했습니다.
- 다만 새 이벤트를 추가할 때마다 리셋 메서드에도 수동으로 추가해야 하고(누락 시 조용히 버그),
  구독자가 많아지면 "이 이벤트를 누가 듣고 있는지" 추적이 어려워질 것이 걱정입니다.

**질문**
1. 프로젝트가 커졌을 때 static 이벤트 허브의 실제 한계가 무엇인지, 실무에서는 어느 규모부터
   다른 방식(ScriptableObject 이벤트 채널, 메시지 버스, DI 컨테이너 등)으로 넘어가는지 궁금합니다.
2. 지금 방식을 유지한다면, 이벤트가 늘어날 때 관리(리셋 누락 방지, 구독 추적)를 위해
   미리 잡아둘 규칙이 있을지 궁금합니다.

## 4. 상태 머신의 경계 — 공격은 왜 상태가 아닌가

**현재 구현**
- 플레이어 상태는 `Free` / `Roll` / `Hit` / `Dead` 네 가지입니다.
- 공격·콤보·스킬은 별도 상태가 아니라, Free 상태에서 `PlayerCombat`이 처리합니다.
  공격 중 이동 제한은 `Player.LockMovement()/UnlockMovement()`로 조율하고,
  스킬 시전 중 평타 차단은 `IsCastingSkill` 같은 플래그로 막습니다.
- 반면 몬스터는 `Idle / Patrol / Detect / Chase / Attack / Hit / Dead`로 공격이 상태입니다.

**우리의 선택과 이유**
- 플레이어 공격은 "이동과 겹칠 수 있는 행동"(이동 중 공격 입력 버퍼, 콤보 유지)이라
  이동 상태와 직교로 두는 게 자연스럽다고 봤습니다.
- 다만 그 결과 Free 상태가 사실상 "이동 + 전투 전부"를 담게 되었고, 전투 관련 플래그
  (`IsCastingSkill`, 이동 잠금, 입력 버퍼)가 상태 머신 밖에서 늘어나는 중입니다.
  새 행동(예: 가드, 차지 공격)이 추가될 때 어느 쪽에 둘지 기준이 애매해지고 있습니다.

**질문**
1. 플레이어 공격을 `AttackState`로 뽑는 것과 지금처럼 컴포넌트+플래그로 두는 것,
   실무 기준으로 어느 쪽이 유지보수에 유리한지 궁금합니다.
2. "상태로 만들 것 vs 플래그/컴포넌트로 둘 것"을 가르는 실무적 판단 기준이 있다면 알고 싶습니다.

## 5. 데이터/에셋 운영 기준 검증

**현재 구현**
- JSON 테이블: `IDataRow` 행 + `JsonManager`가 Addressables `TextAsset`을 비동기 로드·검증·캐싱.
- 자체 기준을 세웠습니다.
  - JSON으로 뽑는 것: 기획자가 바꿀 밸런스 수치, 종류가 늘어나는 데이터
    (우선순위: 몬스터 스탯 > 스킬 > 아이템/드랍 > 퀘스트 > 플레이어 스탯).
  - 인스펙터에 남기는 것: 프리팹·Transform 참조, 히트박스 배치, 연출 감각 값, 시스템 튜닝 값.
  - Addressables 그룹은 자산 종류가 아니라 **수명 기준**으로 분류
    (항상 메모리에 있는 것은 제외, 씬 단위로 바뀌는 것만 등록, 공유 자원은 Shared 그룹).
  - 프리팹은 주소 문자열로 `LoadAssetAsync` 1회 로드 후 풀링(`PooledSpawner`)으로 인스턴스화.
    `InstantiateAsync`는 풀링과 참조 카운트가 충돌해서 쓰지 않기로 했습니다.
- asmdef(어셈블리 정의)는 현 규모에서 도입하지 않기로 결정했습니다
  (컴파일 시간 이득이 없고, Player↔Enemy 상호 참조 구조상 리팩토링 비용만 발생한다고 판단).

**질문**
1. "밸런스 수치는 JSON, 시스템 튜닝 값은 인스펙터"라는 분리 기준이 실무 관행과 맞는지,
   놓치고 있는 예외가 있는지 궁금합니다.
2. Addressables를 수명 기준으로 그룹핑하는 방침이 맞는지, 규모가 커질 때 주의할 점이 있는지 궁금합니다.
3. asmdef 미도입 결정이 적절한지, 도입한다면 어느 시점·어떤 단위가 실무적으로 적당한지 궁금합니다.

## 6. 아직 없는 시스템의 설계 방향 (구현 전 사전 질문)

**현재 구현**
- `ItemData`/`QuestData`(데이터 행)와 `InventoryEvents`/`QuestEvents`(이벤트 허브)까지만 있고,
  실제 인벤토리·퀘스트 시스템 본체는 구현 전입니다.
- 세이브/로드는 아직 전혀 없습니다. 프로젝트에 SQLite 패키지(sqlite-net)는 포함되어 있습니다.

**우리의 선택과 이유**
- 만들고 나서 구조를 고치는 비용이 크기 때문에, 본 구현 전에 방향을 확인하고 싶습니다.

**질문**
1. 인벤토리를 만들 때 아이템 "정의(테이블)"와 "인스턴스(소지 수량·강화 상태)"의 분리를
   처음부터 어떻게 잡는 게 좋은지 궁금합니다.
2. 퀘스트 진행 상태 추적은 이벤트 허브 구독 방식으로 충분한지, 별도 퀘스트 매니저/조건 시스템이
   필요한 규모의 기준이 있는지 궁금합니다.
3. 세이브/로드는 어느 시점부터 넣어야 나중에 고생을 안 하는지, 그리고 저장 대상(스탯, 인벤토리,
   퀘스트 진행, 씬 상태)을 처음부터 어떤 구조(직렬화 방식, SQLite vs JSON 파일)로 잡는 게 좋은지 궁금합니다.

## 7. 성능/최적화 점검 시점

**현재 구현**
- 런타임 할당을 줄이기 위해 미리 해둔 것들:
  - 전투 판정: 미리 할당한 `Collider[64]` 버퍼 + `OverlapBoxNonAlloc`
  - 투사체·이펙트·데미지 텍스트: `PooledSpawner` 기반 풀링
  - SFX: AudioSource 풀 재사용
  - Animator 파라미터: `StringToHash` 캐싱, 히트박스 슬롯: Dictionary 1회 구축
  - 투사체 적중 콜백: 발사마다 람다를 만들지 않도록 델리게이트 캐싱

**우리의 선택과 이유**
- "런타임 할당 최소화"는 처음부터 습관으로 잡는 게 싸다고 판단해서 미리 적용했습니다.
- 다만 아직 프로파일링을 해본 적이 없어서, 지금 수준이 과한지/부족한지 판단 기준이 없습니다.

**질문**
1. 지금 단계(수직 슬라이스 규모)에서 미리 잡아둘 최적화와, 나중에 프로파일링으로 확인한 뒤
   해도 되는 최적화를 가르는 기준이 궁금합니다.
2. 프로파일링을 습관으로 잡는다면, 어느 시점에 무엇부터(프레임 타임, GC 할당, 드로우콜)
   보기 시작하는 게 좋은지 궁금합니다.

## 8. 폴더 구조와 에셋(리소스) 관리

**현재 구현**
- `Assets/Scripts`는 기능별 폴더(= 네임스페이스)로 정리 규칙이 잡혀 있지만,
  스크립트 외 에셋은 종류별 폴더(`Prefabs`, `Animator`, `Effect`, `Materials`, `Scenes`...)에
  넣는 방식이고 명확한 규칙 없이 커져 온 상태입니다. 구체적으로:
  - `Scenes/` 안에 실제 게임 씬(Bootstrap, InGame, Dungeon...)과 팀원별 작업 폴더(GC, JS, MJ, TH)가
    섞여 있습니다.
  - `Prefabs/` 루트에 낱개 프리팹과 하위 폴더(Dungeon, UI, Village)가 섞여 있습니다.
  - `Animator/`에 .fbx, .anim, .controller가 한 폴더에 섞여 있고, 네이밍도 제각각입니다
    (`Combo_Attack_03_01.anim`, `CLazy@Mvm_Walk.FBX`, 공백 포함 `NPC Idle.controller` 등).
  - 외부 에셋은 자체 규칙이 있습니다: **원본은 전부 `ExternalAssets/`에 두고
    (.gitignore로 깃 추적 제외 — 각자 로컬에만 존재), 커스텀하거나 수정해서 쓰는 것만
    밖으로 빼서 우리 폴더 체계로 분류해 깃으로 공유**합니다.
    다만 경계가 새는 지점이 생기고 있습니다 — `Assets/Synty`와 `ExternalAssets/Synty`가
    둘 다 존재하고(최상위 Synty는 ignore 대상이 아니라 깃에 올라감),
    `ExternalAssets/` 루트에 낱개 프리팹(SM_Prop_* 등)과 이미지가 굴러다니며,
    `Assets/DownloadCache/`의 .unitypackage 원본은 깃에 커밋되어 있습니다.
  - `Resources/` 폴더에 AudioMixer가 있습니다 (Addressables 통일 방침과의 관계 확인 필요).
- 리소스 로딩은 Addressables로 통일하는 방침이지만, 위처럼 폴더·이름 규칙은 아직 없습니다.

**우리의 선택과 이유**
- 스크립트는 "폴더 = 네임스페이스" 규칙으로 정리에 성공한 경험이 있어서,
  에셋 쪽도 규칙을 세우고 싶은데 기준을 무엇으로 잡을지(종류별 vs 기능/캐릭터별)가 고민입니다.
- 외부 에셋을 "원본은 `ExternalAssets/`(깃 제외)에 보존, 수정본만 밖으로 승격"으로 나눈 이유:
  원본을 건드리지 않으면 에셋 패키지를 재임포트·업데이트해도 커스텀이 날아가지 않고,
  대용량 원본 팩이 저장소를 불리지 않으며, 깃에 올라간 것만 보면
  "우리가 손대서 책임지는 에셋"이 무엇인지 구분되기 때문입니다.
- 팀원 4명이 각자 브랜치에서 작업하다 보니 팀원별 작업 폴더가 생겼는데,
  이게 임시 방편인지 실무에서도 쓰는 방식인지 모르겠습니다.

**질문**
1. 폴더 구조의 실무 기준이 궁금합니다 — 자산 종류별(`Prefabs/`, `Materials/`...)로 갈지,
   기능·캐릭터별(`Characters/Haru/` 아래에 프리팹+애니+머티리얼)로 갈지, 혼합이라면 경계를 어디에 두는지.
2. "원본은 깃 제외 벤더 폴더에 보존, 수정본만 밖으로 승격해 깃 공유"라는 우리 외부 에셋 규칙이
   실무 방식과 맞는지 궁금합니다. 특히:
   - 밖으로 뺀 수정본(깃에 올라감)이 여전히 `ExternalAssets/`(깃 제외) 안의 머티리얼·텍스처를
     참조하면, 해당 팩이 없는 팀원에게는 참조가 깨집니다. 의존성까지 같이 빼야 하는지(복제 비용)
     vs 참조를 유지하고 팩 설치를 전제하는지, 실무 기준이 궁금합니다.
   - 팀원 간 원본 팩 동기화는 현재 트렐로로 합니다: 외부 에셋을 쓸 사람이
     **원본 파일 + 메타파일을 압축해 트렐로에 올리고**, 팀원들이 받아서 `ExternalAssets/`에
     푸는 방식입니다(메타 포함이라 GUID가 유지되어 참조가 안 깨짐). 이 수동 공유 방식이
     실무에서도 통용되는지, 규모가 커지면 어떤 방식(팩 목록 매니페스트, 별도 스토리지,
     UPM 사설 레지스트리 등)으로 넘어가는지 궁금합니다.
   - 수정본이 어느 팩의 어떤 원본에서 왔는지 기록(출처 추적)은 어떻게 관리하는지 궁금합니다.
3. 팀원별 작업 씬/폴더(GC, JS, MJ, TH)는 실무에서도 쓰는 방식인지, 쓴다면 본 씬으로
   합치는 규칙을 어떻게 잡는지 궁금합니다.
4. 에셋 네이밍 컨벤션(접두사 규칙, 공백 금지 등)을 지금이라도 세우고 일괄 리네임할 가치가 있는지,
   리네임 시 씬/프리팹 참조가 깨지지 않게 주의할 점이 있는지 궁금합니다.
5. Addressables로 통일하는 방침에서 `Resources/` 폴더는 완전히 비우는 게 맞는지,
   AudioMixer처럼 남겨도 되는 예외가 있는지 궁금합니다.
6. `ExternalAssets/` 말고도 깃에서 빼야 할 것이 더 있는지 — Unity 프로젝트에서
   .gitignore 범위를 잡는 실무 체크리스트가 궁금합니다.
